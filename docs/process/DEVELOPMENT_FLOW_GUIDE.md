# 개발 Flow 가이드 (Development Flow Guide)

> **목적:** PRD 기반 Phase 개발, 자체 테스트, 실기기 검증, 문서화, 커밋·push까지 **동일한 절차**로 반복 가능한 개발 방식을 정의합니다.  
> **적용:** Reboot Map에서 검증된 방식이며, **신규 프로젝트에도 그대로 복사·적용**할 수 있습니다.  
> **관련:** [`DEVELOPMENT_PROCESS.md`](DEVELOPMENT_PROCESS.md) — Reboot Map 프로젝트 운영 세부 규칙

---

## 1. 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **PRD가 마스터** | 제품 방향·도메인·Phase 개요는 `PRD.md` 한 곳에서 관리 |
| **Phase 단위 납품** | 한 번에 전체가 아니라 Phase마다 구현 → 테스트 → 문서 → 커밋 |
| **문서 = 게이트** | 코드만 완료가 아니라 **리포트·체크리스트·README**까지 갱신해야 Phase 완료 |
| **자체 테스트 선행** | 실기기 전에 **전체 단위 테스트(회귀 포함)** PASS |
| **실기기는 사용자 게이트** | 에뮬레이터·단위 테스트로 대체 불가한 UX·크래시는 실기기에서 확인 |
| **AI + 사람 협업** | AI는 구현·자체 테스트·문서 초안, **실기기·최종 판단·push 승인**은 사람 |

## 2. 신규 프로젝트 시작 — 문서·폴더 구조

새 저장소를 만들 때 아래 구조를 **최초 커밋**에 포함합니다.

```
<project-root>/
├── README.md                          # 빌드 방법 · Phase 현황 · 체크리스트
├── docs/
│   ├── PRD.md                         # L0 마스터 요구사항
│   ├── README.md                      # 문서 인덱스
│   ├── process/
│   │   ├── DEVELOPMENT_FLOW_GUIDE.md  # 본 가이드 (이 파일)
│   │   └── DEVELOPMENT_PROCESS.md     # 프로젝트별 운영 규칙 (선택·커스터마이즈)
│   ├── phases/
│   │   ├── PHASE-01.md
│   │   ├── PHASE-02.md
│   │   └── ...
│   ├── reports/
│   │   ├── phase-01-test-report.md
│   │   └── ...
│   └── templates/
│       ├── PHASE_TEMPLATE.md
│       └── TEST_REPORT_TEMPLATE.md
└── app/  (또는 src/)                   # 실제 코드
```

### 2.1 문서 계층 (L0 ~ L3)

| 계층 | 파일 | 역할 | 갱신 시점 |
|------|------|------|-----------|
| **L0** | `docs/PRD.md` | 비전, 도메인, Phase 로드맵, 비기능 요건 | Phase 추가·방향 변경 시 |
| **L1** | `docs/phases/PHASE-NN.md` | 해당 Phase 상세 요건, AC, 실기기 체크리스트 | Phase 착수·완료 시 |
| **L2** | `docs/reports/phase-NN-test-report.md` | 자체·실기기 테스트 결과, 이슈·조치 | 테스트마다 |
| **L3** | `README.md` (루트) | 현재 버전, Phase 표, 빌드·체크리스트 | Phase 커밋 전 |

**분리 규칙:** PRD에는 **무엇을 왜** 만드는지만 두고, **어떻게 구현했는지·테스트 수치**는 Phase 문서와 리포트에 둡니다.

## 3. PRD 작성 가이드 (`docs/PRD.md`)

신규 프로젝트 PRD에 **최소한** 포함할 섹션:

1. **제품 비전** — 한 줄 가치 + MVP 범위
2. **기술 스택** — 언어, UI, 아키텍처, 테스트 프레임워크
3. **도메인 모델** — 핵심 엔티티·규칙 (표 또는 목록)
4. **Phase별 개발 계획** — Phase 1~N 목표·산출물·완료 기준 요약
5. **비기능 요건** — 성능, 오프라인, 보안, APK 크기 등
6. **테스트 전략** — 단위·회귀·실기기 게이트
7. **관련 문서 링크** — 본 Flow 가이드, Phase 문서, 리포트

PRD 상단 메타데이터 예시:

```markdown
> **프로젝트명:** MyApp
> **플랫폼:** Android (Kotlin)
> **개발 방식:** Phase 단위 → 자체 테스트 → 실기기 검증 → 커밋
> **관련:** [개발 Flow 가이드](process/DEVELOPMENT_FLOW_GUIDE.md)
```

## 4. Phase 개발 절차 (표준 Flow)

```
┌─────────────────────────────────────────────────────────────┐
│ 0. Phase 착수                                                │
│    PRD 확인 → PHASE-NN.md 작성/갱신 (요건·AC·체크리스트)    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. 구현                                                      │
│    Domain(순수 로직) 우선 · TDD 권장 · UI는 기존 패턴 따름   │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 자체 테스트                                               │
│    전체 테스트 스위트 실행 (이전 Phase 회귀 포함)            │
│    phase-NN-test-report.md 자체 테스트 섹션 기록             │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 실기기 테스트 (또는 1차 탐색 → 보완 → 정식 일괄)          │
│    PHASE-NN.md 체크리스트 검증                               │
│    리포트 실기기 섹션 · 이슈 ID(I-NN) 기록                   │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. 문서 갱신                                                 │
│    PHASE-NN · 리포트 · docs/README · 루트 README · 버전    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. git commit (사용자 요청 시) → push (사용자 요청 시)       │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
                    [다음 Phase]
```

### 4.1 Phase 착수 전 체크

- [ ] 이전 Phase **자체 테스트** PASS (실기기는 프로젝트 정책에 따름)
- [ ] `PHASE-NN.md`에 In/Out Scope·AC·체크리스트 확정
- [ ] `versionName` / 태그 규칙 합의 (예: `1.2.0-phase3`)

### 4.2 Phase 완료 정의 (Definition of Done)

- [ ] 산출물 체크리스트 전항목 `[x]`
- [ ] `.\gradlew.bat test` (또는 프로젝트 테스트 명령) **BUILD SUCCESSFUL**
- [ ] `phase-NN-test-report.md` 요약·테스트 목록·결론 작성
- [ ] 실기기 체크리스트 통과 **또는** 일괄 검증 일정 문서화
- [ ] 루트 `README.md` Phase 현황표 갱신
- [ ] (선택) 사용자 승인 후 commit · push

## 5. 자체 테스트 (Self-test)

### 5.1 실행

```powershell
# 프로젝트 루트에서
.\gradlew.bat test
```

### 5.2 회귀 정책

- **매 Phase 완료 시** 이전 Phase 테스트를 **포함한 전체** 스위트 재실행
- 신규 테스트 ID 규칙 예: `P3-T01`, `T25` (엔진), `I4-01` (실기기 이슈)

### 5.3 리포트에 기록할 항목

| 항목 | 예시 |
|------|------|
| 실행 일시 | 2026-06-06 |
| 총 건수 | 52건 PASS |
| 신규 테스트 | `AssetMatchingEngineTest` 3건 |
| 회귀 | Phase 1~3 포함 전체 PASS |
| 빌드 결과 | BUILD SUCCESSFUL |

## 6. 실기기 테스트 (Device Test Gate)

### 6.1 기본 규칙

- Phase 문서 **§실기기 체크리스트** 전항목 검증
- 통과: `[x]`, 미통과: 원인·이슈 ID·조치 상태를 리포트에 기록
- **미통과 시** 동일 Phase 내 보완 후 재검증 (다음 Phase 착수 지연)

### 6.2 1차 탐색 + 정식 일괄 (Reboot Map에서 사용한 변형)

대규모 Phase가 연속일 때:

1. **코드 완료 + 자체 테스트 PASS** 후 다음 Phase 착수 허용
2. **1차 실기기 탐색** — 주요 화면·크래시만 확인, 이슈 즉시 보완
3. **정식 일괄 검증** — 여러 Phase 체크리스트를 한 번에 수행 (일정을 PRD·리포트에 명시)

문서에 반드시 적을 문구 예:

> 실기기 정식 검증: YYYY-MM-DD 예정 (Phase 3·4 일괄)

### 6.3 실기기 이슈 기록 형식

| ID | 이슈 | 조치 | 상태 |
|----|------|------|------|
| I4-03 | PDF 공유 Application Context 크래시 | Activity Context로 공유 | ✅ |

## 7. AI 협업 시 권장 패턴

Reboot Map에서 효과적이었던 방식:

| 단계 | AI | 사용자 |
|------|-----|--------|
| 요건 정리 | PRD·Phase 초안 보조 | 범위·우선순위 확정 |
| 구현 | TDD·도메인·UI·리팩터 | 방향 피드백·실기기 확인 |
| 자체 테스트 | `gradlew test` 실행·실패 수정 | 결과 확인 |
| 실기기 | 스택트레이스 기반 수정 제안 | **직접 기기에서 검증** |
| 문서 | 리포트·README·Phase 갱신 | 검증 일정·승인 |
| Git | commit 메시지 초안·push (요청 시) | **commit/push 시점 결정** |

**권장 대화 흐름**

1. «Phase N 순차 진행» — AI가 PHASE-N.md 기준 구현
2. «실기기에서 ○○ 확인» — 이슈 공유 시 스택트레이스 첨부
3. «문서 반영 후 commit» — 문서+코드 한 커밋
4. «실기기는 내일» — 리포트에 일정만 명시, 게이트 유지

## 8. 커밋 · Push 절차

### 8.1 커밋 전 체크리스트

- [ ] `docs/phases/PHASE-NN.md` — 상태·산출물·AC
- [ ] `docs/reports/phase-NN-test-report.md` — 테스트·실기기(또는 예정)
- [ ] `docs/README.md` — Phase 현황표
- [ ] `README.md` — 버전·체크리스트·커밋 이력 요약
- [ ] `app/build.gradle.kts` — `versionName` (해당 시)
- [ ] 민감 정보(`.env`, 키) 미포함

### 8.2 커밋 메시지 형식

```
Phase N: <한 줄 요약>

<왜/무엇을 1~2문장. 테스트 N건 PASS, 문서 경로>
```

예:

```
Phase 4: 목돈 타임라인·자산매칭·PDF 리포트

목돈 CashFlowEngine 연동·MilestoneTimelineCard·PDF 공유 구현.
실기기 1차 보완 5건 반영. 52건 PASS. phase-04-test-report.md 갱신.
```

fix 전용:

```
fix: <증상 한 줄>

<원인·조치 한 줄>
```

### 8.3 Push

- **사용자가 명시적으로 요청할 때만** `git push`
- push 전: `git status`, 로컬이 origin 대비 앞선 커밋 확인
- `main` force push 금지 (예외 없으면)

- [ ] `docs/templates/` 복사 (`PHASE_TEMPLATE`, `TEST_REPORT_TEMPLATE`)

- [ ] `docs/README.md` 인덱스 + Phase 1 행 추가
- [ ] 루트 `README.md`에 «문서 관리» 표 링크
- [ ] `PHASE-01.md` + `phase-01-test-report.md` 생성

## 11. Reboot Map 참고 사례

| Phase | 핵심 산출 | 자체 테스트 | 실기기 |
|-------|-----------|-------------|--------|
| 1 | CashFlowEngine, 기본 UI | 15건+ | ✅ |
